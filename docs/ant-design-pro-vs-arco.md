  # Ant Design Pro 与 Arco Enterprise Admin 对比

  ## 1. 结论

  对于企业管理后台，ant-design-pro 和 Arco 都能满足基础开发需求，但侧重点不同：

  - ant-design-pro 更适合快速搭建大量标准 CRUD 页面。
  - Arco 更适合重视视觉一致性、代码显式性、细粒度权限和 OpenAPI 契约的项目。
  - 结合当前项目偏好、Java 后端和已经实现的权限模型，建议继续使用 Arco，并吸收 Ant Design Pro 的页面抽象经验。

  ## 3. 代码质量与工程设计

  ### ant-design-pro

  优点：

  - Umi Max 约定较多，页面接入速度快。
  - 路由、布局、菜单和运行时初始化有成熟约定。
  - 官方示例丰富，团队容易复制已有页面。
  - ProComponents 对列表、表单、详情页有较强复用能力。

  不足：

  - 对 Umi Max 插件体系依赖较深。
  - 部分行为由约定和插件隐式提供，定位问题需要理解 Umi 运行机制。
  - 业务逻辑容易分散在运行时配置、路由配置和页面文件中。
  - 如果脱离 Umi 生态，迁移成本相对较高。

  ### 当前 Arco 项目

  优点：

  - Vite、React Router、React Query 和 TypeScript 边界清晰。
  - 路由、权限、API 请求和页面逻辑更加显式。
  - OpenAPI 契约可以生成类型安全的请求客户端。
  - 更容易让 AI 定位单个文件、理解调用链和修改局部逻辑。
  - 框架耦合较低，未来可以替换部分基础设施。

  不足：

  - 企业级列表、表单和详情抽象仍需要继续建设。
  - 页面规范需要由项目团队主动维护。
  - 没有 ProComponents 那样成熟的一站式业务组件层。
  - 路由、菜单和权限如果分别配置，长期可能出现配置漂移。

  ## 4. 权限能力对比

  ### ant-design-pro 默认能力

  Ant Design Pro 的权限机制主要用于前端访问控制：

  - 菜单显示控制。
  - 路由访问控制。
  - 按钮或组件显示控制。
  - 基于用户状态计算 access 权限。

  典型方式：

  const access = {
    canAdmin: user?.role === 'admin',
  };

  默认并不包含完整的角色权限管理闭环：

  - 权限点字典。
  - 角色权限点编辑。
  - 权限保存接口。
  - 数据范围。
  - 与后端权限模型的同步。

  ### 当前 Arco 项目能力

  当前 Arco 项目已经实现：

  - `resource:action` 权限模型。
  - `all`、`any` 和 `*` 通配权限。
  - 菜单权限过滤。
  - 路由级 403。
  - 操作级 `<Permission>` 组件。
  - `roles:read` 和 `roles:write`。
  - 角色权限点勾选和保存。
  - 角色数据范围：
    - `all`
    - `department`
    - `self`
  - OpenAPI 角色接口。
  - Mock API 权限校验。
  - 角色保存后的刷新持久化。

  因此，在细粒度 RBAC 方面，当前 Arco 实现已经超过 Ant Design Pro 默认脚手架。

  需要注意：前端权限只负责界面体验，生产环境必须由 Java 后端在 Spring Security、Controller 和 Service 层再次校验。

  ## 5. 页面开发效率

  ### ant-design-pro 的优势

  如果系统包含大量以下页面，Ant Design Pro 通常更快：

  - 查询列表。
  - 分页表格。
  - 新增和编辑表单。
  - 详情页。
  - 批量操作。
  - 状态标签和工具栏。
  - 标准后台布局。

  原因是 ProTable、ProForm、ProLayout 已经提供了大量通用能力。

  ### Arco 当前的不足

  当前 Arco 项目需要补齐以下企业级基础组件：

  - `DataTable`：统一分页、筛选、排序、列配置和批量操作。
  - `QueryForm`：统一查询表单布局和重置行为。
  - `CrudDrawer`：统一新增、编辑抽屉和提交状态。
  - `DetailPanel`：统一详情展示。
  - `PageHeader`：统一页面标题、面包屑和操作区。
  - `EmptyState`、`ErrorState` 和 `LoadingState`：统一页面状态。

  ## 6. 请求层与 Java 后端适配

  ### ant-design-pro

  优点：

  - 请求调用简单。
  - 适合快速调用 REST API。
  - Umi 项目中代理、请求拦截和运行时配置较成熟。

  不足：

  - 默认不会自动生成后端类型。
  - 接口模型需要手动维护，前后端契约容易漂移。
  - 对大型 Java API 项目，需要额外引入 OpenAPI 生成方案。

  ### 当前 Arco 项目

  当前采用：

  ```text
  OpenAPI Schema
      ↓
  Orval
      ↓
  TypeScript API Client
      ↓
  React Query
      ↓
  页面组件
  ```

  优势：

  - 与 Spring Boot OpenAPI 文档更容易对接。
  - 请求参数和返回值具备类型约束。
  - 接口变更可以通过重新生成客户端发现。
  - React Query 负责缓存、请求状态和失效刷新。
  - 更适合长期维护的前后端契约。

  ## 7. AI 友好度

  ### ant-design-pro

  优势：

  - 网上示例和资料非常多。
  - 常见页面可以快速参考官方模板。
  - 组件生态成熟。

  不足：

  - Umi 插件、运行时配置和约定较多。
  - 同一个行为可能由多个配置层共同决定。
  - AI 修改时需要同时理解 Umi、Max、Ant Design 和 ProComponents。

  ### 当前 Arco 项目

  优势：

  - 技术栈更接近标准 React 应用。
  - 路由和权限代码显式。
  - API 客户端由 OpenAPI 生成，模型边界明确。
  - 文件职责较容易划分。
  - 更适合让 AI 按功能模块进行定位、修改和测试。

  不足：

  - 项目自定义抽象越多，越需要同步维护开发文档。
  - 缺少统一页面模板时，AI 可能生成风格不一致的页面。
  - 需要建立明确的目录和组件约定。

  ## 9. 当前 Arco 项目的能力进展

  以下方向已在前端仓库落地，具体实现和新增页面流程见 [页面开发指南](page-development-guide.md)，规划背景见 [能力路线图](capability-roadmap/analysis-report.md)：

  1. route manifest 统一了路由、菜单、面包屑与页面权限。
  2. `ApiError` 区分 401、403、网络、服务端和字段校验错误；OpenAPI 与生成结果由 CI 检查。
  3. 用户管理页使用 `DataTable`、`QueryForm`、`CrudDrawer` 和 `DetailPanel`；官方查询表格页展示本地数据复用。
  4. 中文开发指南覆盖目录、请求、权限、页面状态、视觉和验收，关键页面运行少量截图断言。

  Java 服务端的 Spring Security 权限、数据范围和 `/v3/api-docs` 仍需由真实后端独立落地与测试；前端 MSW 或 E2E 不能替代服务端安全契约验证。

  ## 10. 选型建议

  推荐继续使用 Arco，原因如下：

  - 已经符合项目对 Arco 视觉风格的偏好。
  - 当前权限模型比 Ant Design Pro 默认能力更完整。
  - OpenAPI + Orval 更适合 Java 后端契约管理。
  - Vite + React Router 的显式架构更便于长期维护。
  - AI 更容易理解和修改当前代码结构。
  - 不需要为了获得 ProTable 和 ProForm 而迁移整个技术栈。

  建议借鉴 Ant Design Pro 的部分：

  - 标准化列表页结构。
  - 查询表单和表格联动。
  - 抽屉式新增、编辑流程。
  - 详情页和操作区布局。
  - 通用页面状态组件。
  - 页面级权限和操作级权限的组合方式。

  ## 11. 最终结论

  如果项目目标是“快速批量生成标准后台页面”，选择 ant-design-pro 更省初始开发成本。

  如果项目目标是“保持 Arco 视觉、建设细粒度权限、对接 Java 后端、保证契约类型安全并长期维护”，当前 Arco 项目更适合。

  最终建议：

  > 继续使用 Arco，吸收 Ant Design Pro 的企业级页面抽象和工程经验，不迁移 UI 框架。
