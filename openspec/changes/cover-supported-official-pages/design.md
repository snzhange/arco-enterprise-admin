# Design

## Context

当前正式页面与展示示例混在 `src/pages/official` 等目录中，SearchTablePage 等公共能力已有行为测试，但部分正式页面仍只有渲染级覆盖。实现必须遵循页面开发指南、现有 Vitest/Testing Library 约定，并让测试通过用户可见结果和请求契约验证行为。

## Goals / Non-Goals

**Goals:**
- 建立可审查的正式支持页面清单和覆盖矩阵。
- 为正式页面补齐适用的状态和主要操作测试。
- 让示例页面分类明确，避免覆盖率统计出现隐式缺口。

**Non-Goals:**
- 不重写页面架构或统一所有展示示例的交互。
- 不用快照测试替代业务行为测试。

## Decisions

1. 以页面路由和用户可见业务能力为覆盖单元，清单记录页面类型、权限前置、请求依赖和适用状态。这样可将正式支持边界与目录结构解耦。
2. 优先补齐高风险页面的加载、成功、空、错误、权限和恢复路径，再处理低风险展示页面；替代方案是按文件数量平均分配测试，但无法反映用户风险。
3. 复用现有测试 fixtures、MSW/请求 mock 和权限构造器，断言 DOM 状态及请求参数；不直接断言内部 hook 或实现分支。
4. 将清单作为仓库内可审查文档，并在测试任务中校验每个正式页面至少存在一个行为测试入口；示例页面在清单中标记为隔离范围。

## Risks / Trade-offs

- [页面边界持续变化] -> 在新增路由评审清单同步更新，并把缺失条目标记为失败。
- [测试数量增加导致运行变慢] -> 共享 fixtures、按风险分层运行，避免重复覆盖纯展示结构。
- [mock 与后端契约漂移] -> 对关键请求参数和错误响应保留契约断言，并结合 API 生成流程验证。

## Migration Plan

先提交页面分类和覆盖矩阵，再按业务域逐批新增测试；每批通过 `pnpm test --coverage` 后纳入质量报告。若某页面暂不能纳入正式支持范围，保留示例分类和路线图条目，不删除其现有验证。
