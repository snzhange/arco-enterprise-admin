# Design

## Context

当前 Vite 构建能够产出应用，但资源体积告警与用户实际下载成本没有形成固定预算；工作台轮播图片较大，部分媒体和路由模块在首屏阶段加载。预算必须基于压缩后的真实产物，并允许在审查中解释必要增长。

## Goals / Non-Goals

**Goals:**

- 识别并压缩最大的图片/媒体资源，保持视觉验收结果。
- 通过路由和组件边界延迟非首屏代码与媒体。
- 输出可追踪的 JS/CSS/媒体 gzip 报告和 CI 硬门禁。
- 用 bundle 分析定位重复依赖和意外引入。

**Non-Goals:**

- 不改变页面功能、接口响应或业务数据。
- 不以 Lighthouse 单次分数替代构建产物预算。
- 不在没有报告和评审记录时自动提高预算阈值。

## Decisions

### 1. 以 gzip 产物作为主要预算指标

gzip 更接近线上传输成本，同时保留原始字节和文件数量作为辅助指标。只看原始 bundle 容易高估或低估实际网络开销；只看性能分数又难以定位具体文件。

### 2. 先处理资源，再调整代码分割

先对轮播图片做尺寸/格式压缩，随后检查路由和大型依赖的动态边界。这样可以区分静态媒体收益和 JS/CSS 结构收益，避免把所有问题归因于构建器配置。

### 3. 预算配置版本化并在 CI 硬失败

预算文件与基线报告纳入仓库，CI 在生产模式构建后比较 gzip 结果。预算提升必须同时给出原因和报告；不通过提高 Vite warning limit 消除告警。

### 4. 使用可选 bundle analyzer 做定位

分析器只作为诊断工具，不把可视化输出作为门禁输入。门禁读取稳定的机器可读产物，降低工具版本或图表格式变化造成的噪声。

## Risks / Trade-offs

- [Risk] 压缩媒体导致视觉质量下降 → 使用视觉回归和尺寸/质量验收，必要时保留高质量首屏版本。
- [Risk] 延迟加载造成首次切换等待 → 对用户即将访问的相邻内容做有限预取，并用 E2E 验证加载状态。
- [Risk] gzip 预算受压缩器版本影响 → 锁定 Node/压缩工具版本，升级时单独更新基线。

## Migration Plan

1. 生成当前生产构建资源清单和 gzip 基线，确认最大资源与 chunk。
2. 压缩轮播媒体并验证视觉快照，记录前后尺寸。
3. 调整非首屏路由/媒体加载边界，运行功能和视觉 E2E。
4. 引入预算脚本和 CI 门禁，先以报告模式观察一个迭代周期，再启用失败模式。
5. 若回归严重，回滚懒加载或单项媒体变更；保留预算脚本和基线以便继续定位。
